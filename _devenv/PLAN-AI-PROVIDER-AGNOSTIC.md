# طرح — معماری بدون وابستگی به ارائه‌دهندهٔ هوش مصنوعی (Provider-Agnostic)

- **وضعیت:** پیش‌نویس برای تصویب کارفرما — هنوز هیچ کدی تغییر نکرده است
- **تاریخ طرح:** ۱۴۰۵/۰۶/۰۹
- **جانشین:** §۴ِ `ADR-0004` و بخش استنتاج `DESIGN-PADO`
- **بازنگری‌ها:** (۱) بخش‌بندی بارکاری بر پایهٔ تحلیل قابلیت واقعی Groq، نه مثال؛ (۲) هر دو Groq و OpenRouter «api provider» شناخته می‌شوند نه «OpenAI-compatible».

---

## ۱. هدف و معیار پذیرش

۱. هیچ کلاسی از هستهٔ پروژه نامِ هیچ ارائه‌دهنده‌ای را مستقیم صدا نزند؛ هسته فقط با قرارداد درونی خودش حرف می‌زند.
۲. افزودن، حذف یا جابه‌جایی ارائه‌دهنده فقط با یک رکورد تنظیمات انجام شود — بدون تغییر کد.
۳. همهٔ ارائه‌دهنده‌ها یک نوع واحد `api_provider` دارند؛ تفاوت وایر (گویش سیم) زیرفیلد داخلی `protocol` است.
۴. مسیریابی بر اساس **قابلیتِ موردنیازِ هر کار** و **قابلیتِ اعلام‌شدهٔ هر ارائه‌دهنده** انجام شود؛ بخش‌بندی پیش‌فرض از تحلیل Groq در §۵ بیاید، نه از نام سخت‌کدشده.
۵. سیاست کلید/بودجه/گیت‌های `ADR-0004 §۳` (حساب مستقل فروشگاه، کلیدِ runtime، ممنوعیت ذخیره/لاگ) بی‌کم‌وکاست بماند.

## ۲. الگوی استاندارد (بر پایهٔ تحقیق)

الگوی موردتوافق صنعت (LiteLLM، Vercel AI SDK، Portkey، LangChain) ترکیب چهار قطعه است:

```text
Strategy (قرارداد مشترک) + Adapter (ترجمهٔ وایر) + Registry (فهرست ارائه‌دهنده‌ها) + Router (انتخاب بر اساس نیازِ قابلیتی)
```

دو نتیجهٔ استاندارد که طرح بر آن بنا می‌شود:

- هر سرویسِ بیرونی (Groq، OpenRouter، DeepInfra، OpenAI، Anthropic، سرویس اختصاصی) در اصل یک **API provider** است. «OpenAI-compatible» هویتِ ارائه‌دهنده نیست؛ فقط یک گویشِ سیم (wire protocol) است که خیلی از آن‌ها صحبت می‌کنند. پس در پنل، همه «ارائه‌دهندهٔ API» معرفی می‌شوند و گویش، یک فیلد فنیِ داخلی است.
- در عمل فقط **سه آداپتور وایر** لازم است: گویش `openai` (که Groq، OpenRouter، DeepInfra، Together و… صحبت می‌کنند)، گویش `anthropic` (بومی Anthropic) و `custom` (نگاشت JSON برای سرویس اختصاصی). بقیهٔ ارائه‌دهنده‌ها «رکورد تنظیمات» هستند.

## ۳. اجزای جدید

| جزء | نقش |
| --- | --- |
| `AiProviderInterface` (بازنگری) | قرارداد مشترک + `protocol()` و `capabilities()` و `is_configured()` |
| `ProviderDefinition` | value-object یک رکورد ارائه‌دهنده که از تنظیمات خوانده می‌شود |
| `ProviderRegistry` | فهرست رکوردها + ساخت آداپتور متناسب با `protocol` |
| `ProviderRouter` (`AiGateway`) | نگاشت نیازِ قابلیتیِ کار → ارائه‌دهنده، بررسی قابلیت، اجرا و ثبت مصرف |
| `OpenAiProtocolAdapter` | گویش `openai` (پوشش هر endpoint با این گویش، از جمله Groq و OpenRouter) |
| `AnthropicProtocolAdapter` | گویش `anthropic` |
| `CustomProtocolAdapter` | گویش `custom` (پیکربندی‌محور برای api provider اختصاصی) |
| `Workload` | شمارش بخش‌ها با نام ماشینی و عنوان فارسی: `routine` («امور اداری») و `judgment` («مدیریت») — قابل گسترش |
| پنل ادمین | برگهٔ «ارائه‌دهنده‌های API» + بخش «مسیریابی بارکاری پادو» با دو عنوان: «امور اداری» و «مدیریت» |
| `ADR-0005` | سند تصمیم جدید |

`AiRequest`، `AiResult` و `AiToolbox` بدون وابستگی‌اند و **دست‌نخورده** می‌مانند (قرارداد درونی).

## ۴. مدل دادهٔ تنظیمات (کلیدهای پیشنهادی)

```text
pado.ai.providers         آرایهٔ سریال‌شدهٔ رکوردها (یک رکورد برای هر ارائه‌دهنده)
pado.ai.routing.routine   ارائه‌دهندهٔ بخش «امور اداری» (پیش‌فرض: groq)
pado.ai.routing.judgment  ارائه‌دهندهٔ بخش «مدیریت» (پیش‌فرض: openrouter)
pado.ai.default_provider  شناسهٔ پیش‌فرض (وقتی بخشی تنظیم نشده باشد)
```

هر رکورد ارائه‌دهنده:

```text
id                  شناسهٔ یکتا (مثلاً openrouter یا groq)
title               برچسب نمایشی
type                api_provider (نوع واحد برای همه)
protocol            openai | anthropic | custom   ← گویش سیم، انتخاب آداپتور
base_url            نشانی پایه
model_allowlist     فهرست مدل‌های پین‌شده (مسیریابی آزاد مدل مجاز نیست — هم‌راستا با ADR-0004)
default_model       مدل پیش‌فرض
capabilities        فهرست قابلیت‌های اعلام‌شده (chat | tools | json | vision | stt | tts | …)
quality             standard | premium   ← برای بخش‌بندی سبک/سنگین
enabled / benchmark_passed / geo_eligible     گیت‌های فعال‌سازی (پیش‌فرض خاموش)
daily_token_budget  سقف روزانهٔ توکن هر فروشگاه
timeout             مهلهٔ فراخوانی
custom (فقط protocol=custom): request_template، headers، مسیرهای استخراج پاسخ و هزینه
```

کلیدِ API طبق سیاست جاری **در تنظیمات ذخیره نمی‌شود**؛ در `AiRequest` به‌صورت runtime می‌آید (حساب مستقل همان فروشگاه).

## ۵. تحلیل قابلیت Groq و بخش‌بندی بارکاری پادو

پایهٔ تحلیل: مستندات رسمی Groq (۲۰۲۶) + جدول وظایف پادو در `DESIGN-PADO` بند ۱۷ و `ADR-0004 §۱`.

### قابلیت‌های Groq (واقعیت)

| قابلیت | وضعیت روی Groq |
| --- | --- |
| چت/تولید متن (۱۱ مدل متن‌باز، زمینهٔ ۱۳۱K، سرعت LPU) | ✅ دارد |
| فراخوانی ابزار (tool/function calling) — همهٔ مدل‌ها | ✅ دارد |
| خروجی JSON / ساختاریافته — همهٔ مدل‌ها | ✅ دارد |
| ورودی تصویر (vision) | ⚠️ محدود — فقط چند مدل (Llama 4 Scout/Maverick، Qwen3.6/3.8-27B؛ Qwen3-VL فقط Enterprise)؛ تا ۵ تصویر |
| OCR | ⚠️ محدود — فقط از طریق همان مدل‌های vision |
| صدا (STT/TTS) | ✅ دارد (Whisper + TTS) — ورودی صوتی ندارد |
| Embedding / reranking | ❌ ندارد (endpoint جداگانه‌ای ارائه نمی‌کند) |
| تولید تصویر / ویدئو | ❌ ندارد |
| فارسی | خوب برای متن کوتاه/دسته‌بندی؛ نه در سطح frontier برای کپی بلند باکیفیت |

### نام‌گذاری بخش‌ها (تصمیم کارفرما)

| نام ماشینی (کلید مسیریابی) | عنوان فارسی در پنل | ارائه‌دهندهٔ پیش‌فرض |
| --- | --- | --- |
| `routine` | **امور اداری** | groq |
| `judgment` | **مدیریت** | openrouter |

این دو بخش، همان «دو بخش» پنلِ «مسیریابی بارکاری پادو» هستند و هرکدام عنوان بالا را دارند؛ زیر هر عنوان، ادمین ارائه‌دهندهٔ همان بخش را برمی‌گزیند.

### بخش‌بندی بارکاری (نتیجهٔ تحلیل)

**بخش ۱ — «امور اداری» (کلید `routine`) → Groq:**
دسته‌بندی و برچسب‌گذاری محصولات · تعدیل و فیلتر متن · پاسخ سریع تیکت · پیش‌نویس هوک/ایده/سناریو کوتاه · تحلیل احساسات کامنت کوتاه · خلاصه‌سازی کوتاه و گزارش ساده · استخراج ساختاریافته (JSON/tool).

**بخش ۲ — «مدیریت» (کلید `judgment`) → OpenRouter:**
برنامهٔ هفتگی/ماهانه و راهبرد ۳۰/۶۰/۹۰ · ماتریس محتوا · کپشن بلند و محتوای اینستاگرام باکیفیت فارسی · تحلیل عمیق حساب/رقیب و قیف فروش · قیمت‌گذاری و پاسخ شکایت (قضاوت حساس) · ترجمهٔ باکیفیت و یادگیری ترکیبی بلند.

**بخش ۳ — «تخصصی» (خارج از این دو بخش؛ در پنل مسیریابی نمی‌آید):**
embedding/reranking (Groq ندارد) · OCR باکیفیت (Groq محدود) · تصویر/کاروسل/صوت/ویدئو (Groq ندارد؛ در `AiStudio` با سرویس ایرانی) · TTS فارسی باکیفیت (در استودیوی رسانه). این بخش مسیر جداگانه دارد و جزء «دو بخش» پنل مسیریابی نیست.

### اصل مسیریابی

این جدول **سیاست پیش‌فرض در تنظیمات** است، نه منطق سخت‌کدشده. هر کار، یک «نیاز قابلیتی» اعلام می‌کند (مثلاً `quality=premium` یا `vision=required`)؛ هر ارائه‌دهنده هم قابلیت‌هایش را اعلام می‌کند؛ `ProviderRouter` بر اساس تطابق این دو انتخاب می‌کند. نتیجه: اگر فردا مدل فارسی قوی روی Groq آمد یا ادمین پول داد، فقط رکورد تنظیمات عوض می‌شود — بدون تغییر کد.

## ۶. جریان یک درخواست

```text
بارکاری (نیاز قابلیتی)
→ ProviderRouter: تطابق نیاز با قابلیت‌های اعلام‌شده → انتخاب ارائه‌دهنده → رکورد
→ بررسی گیت‌ها (اگر کار tool/vision می‌خواهد و ارائه‌دهنده ندارد → رد صادقانه capability_unsupported)
→ ProviderRegistry: protocol → آداپتور مناسب
→ آداپتور: قالب درونی → گویش ارائه‌دهنده → پاسخ نرمال‌شده
→ AiResult + ثبت مصرف در ig_ai_credit_ledger
```

## ۷. ترجمهٔ گویش‌ها (خلاصه)

| موضوع | protocol=openai (Groq، OpenRouter، …) | protocol=anthropic | protocol=custom |
| --- | --- | --- | --- |
| احراز | `Bearer` | `x-api-key` | از قالب |
| system | پیام `system` | پارامتر جدا | از قالب |
| ابزارها | `tools` | بلوک `tool_use` | در صورت پشتیبانی، از قالب |
| پاسخ | `choices[0].message.content` | `content[0].text` | مسیر JSON پیکربندی‌شده |
| مصرف | `usage.prompt_tokens` و … | `usage.input_tokens/output_tokens` | مسیر JSON پیکربندی‌شده |

نکتهٔ صادقانه: `custom` فقط «نگاشت JSON» است (نه منطق دلخواه)؛ اگر سرویسی به امضا/چرخهٔ مخصوص نیاز داشته باشد، آن مورد خارج از این طرح است و آداپتور اختصاصی می‌خواهد.

## ۸. مهاجرت (از DeepInfra)

۱. `DeepInfraAdapter` و کلیدهای `pado.deepinfra.*` حذف می‌شوند.
۲. به‌جای آن دو رکورد پیش‌فرض `api_provider` سید می‌شوند: `openrouter` (protocol=openai، quality=premium) و `groq` (protocol=openai، quality=standard).
۳. اگر فروشگاهی همچنان DeepInfra بخواهد، آن هم فقط یک رکورد `api_provider` با `protocol=openai` و `base_url` آن است — بدون کد جدید.
۴. گیت بنچمارک فارسی دیگر به یک ارائه‌دهنده گره نیست و روی هر ارائه‌دهندهٔ انتخابی اجرا می‌شود.
۵. مستندات (`ADR-0004`، `DESIGN-*`، `API-KEYS.md`، `PROVIDER-VERIFY.md`) به‌روز می‌شوند.

## ۹. تست

- تست هر آداپتور با پاسخ جعلی همان گویش (openai / anthropic / custom).
- تست `ProviderRouter` (تطابق قابلیت، سقوط به پیش‌فرض، رد `capability_unsupported`، خالی‌بودن کلید).
- `DeepInfraAdapterTest` به تست‌های آداپتورهای جدید تبدیل می‌شود.
- همان آزمون‌های امنیتی (بدون eval/exec، نقش‌های command/data، اعتبارسنجی آرگومان ابزار) حفظ می‌شود.

## ۱۰. راستی‌آزمایی زنده

ورک‌فلوی `github-workflow-provider-verify.yml` بازنویسی می‌شود تا به‌جای سخت‌کدکردن DeepInfra، پروب عمومی هر دو گویش `openai` و `anthropic` را اجرا کند (`OPENROUTER_API_KEY`، `GROQ_API_KEY`، و در صورت وجود کلید Anthropic)؛ پروب Zernio و پاک‌سازی پروفایل یتیم `6a9488fe77555aae011b7a18` هم حفظ می‌شود.

## ۱۱. مراحل اجرا (هر مرحله با «شروع کن» جداگانه)

۱. `ADR-0005` (تصمیم مستند).
۲. هستهٔ بدون UI: قرارداد بازنگری‌شده + `ProviderDefinition` + `ProviderRegistry` + `ProviderRouter` + تست.
۳. سه آداپتور گویش + تست‌هایشان.
۴. مدل تنظیمات + پنل ادمین (برگهٔ ارائه‌دهنده‌های API و مسیریابی بارکاری) با nonce از ماژول Crypto و سقف‌ها در بک‌اند.
۵. مهاجرت و سید `openrouter`/`groq` و حذف DeepInfra.
۶. بازنویسی ورک‌فلو و بنچمارک فارسی روی ارائه‌دهنده‌های انتخابی.

## ۱۲. ریسک‌ها (واقعیت، بدون بزرگ‌نمایی)

- `OpenRouter` واسط است؛ برای دادهٔ مشتری باید ZDR (عدم نگهداری) و پین‌کردن ارائه‌دهندهٔ زیرین در رکورد اجباری شود تا با روح `ADR-0004 §۳` نسازد.
- ترجمهٔ ابزارها به گویش Anthropic دقیق‌تر از OpenAI است و باید جداگانه آزمون شود.
- قابلیت‌ها باید «اعلام‌شده در رکورد» باشند نه فرض‌شده؛ ردِ صادقانهٔ `capability_unsupported` بهتر از تولید ناقص است.
- `quality` یک سیاست ادمین است، نه معیار سخت‌افزاری؛ در بنچمارک فارسی باید هر ارائه‌دهنده برای هر دسته واقعاً سنجیده شود.

## ۱۳. طراحی ثبت کلیدها و ویزارد تغییر ارائه‌دهنده (الگوی Cline)

دو سطح جدا از هم:

۱. **صفحهٔ «ثبت کلیدها»** در تب تنظیمات پادو — ساده و ثابت: نام دو ارائه‌دهندهٔ جاری + دو تکست‌باکس کلید + یک دکمهٔ «ثبت کلیدها» + یک آیکون ⚙.
۲. **پنل «تغییر ارائه‌دهنده»** (بازشونده با ⚙) — شبیه Cline: دو بخش «امور اداری»/«مدیریت»، کلید «استفاده از یک ارائه‌دهنده برای هر دو بخش»، و انتخاب ارائه‌دهنده/مدل برای هر بخش.

کلید فقط در مخزن کلیدِ پنل ذخیره می‌شود (الگوی `keyRef` موجود در `DESIGN-PADO` بند ۷۱۸ و 914).

### ۱۳.۱ صفحهٔ «ثبت کلیدها» (نمای اولیهٔ تب تنظیمات پادو)

```text
┌─ پادو — ثبت کلیدها ──────────────────────────────────────────┐
│                                                              │
│  Groq        :  [ _______________________________ ]          │
│  OpenRouter  :  [ _______________________________ ]          │
│                                                              │
│                              [ ثبت کلیدها ]          ⚙       │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

- در ابتدا **نام دو ارائه‌دهندهٔ پیش‌فرض** نمایش داده می‌شود: Groq (بخش «امور اداری») و OpenRouter (بخش «مدیریت»). اگر در پنل ⚙ ارائه‌دهنده عوض شود، نام‌های همین دو ردیف به‌روز می‌شوند.
- کنار هر نام **یک تکست‌باکس** برای درج API Key (مقدار maskشده؛ مقدار واقعی فقط لحظهٔ تایپ در مرورگر است).
- **فقط یک دکمهٔ «ثبت کلیدها»** که هر دو کلید را با هم ذخیره می‌کند (الگوی keyRef؛ بدون لاگ/نمایش مقدار).
- **فقط یک آیکون ⚙** که پنل «تغییر ارائه‌دهنده» را باز می‌کند.
- پس از ثبت، نتیجه به‌صورت notice ادمین (موفق/خطا) نمایش داده می‌شود؛ هم‌زمان یک تست اتصال سبک (همان پروب راستی‌آزمایی) اجرا و نتیجهٔ «متصل/خطا» کنار هر نام نشان داده می‌شود.

### ۱۳.۲ پنل «تغییر ارائه‌دهنده» (بازشونده با ⚙ — الگوی Cline)

```text
┌─ تغییر ارائه‌دهنده ─────────────────────────────────────────────┐
│  ☐ استفاده از یک ارائه‌دهنده برای هر دو بخش                       │
│                                                               │
│  ┌─ امور اداری (routine) ─────────────────────────────────┐   │
│  │  ارائه‌دهنده: [ Groq ▼ ]                                │   │
│  │  مدل:        [ llama-3.3-70b-versatile ▼ ]             │   │
│  └────────────────────────────────────────────────────────┘   │
│                                                               │
│  ┌─ مدیریت (judgment) ────────────────────────────────────┐   │
│  │  ارائه‌دهنده: [ OpenRouter ▼ ]                          │   │
│  │  مدل:        [ <مدل پیش‌فرض پین‌شده> ▼ ]                 │   │
│  └────────────────────────────────────────────────────────┘   │
│                                                               │
│                                   [ذخیره]  [انصراف]            │
└───────────────────────────────────────────────────────────────┘
```

- کلید «استفاده از یک ارائه‌دهنده برای هر دو بخش» روشن ← بخش «مدیریت» فقط‌خوان و تابع «امور اداری» می‌شود.
- دابل‌دان ارائه‌دهنده: فهرست ارائه‌دهنده‌های ثبت‌شده (پیش‌فرض Groq / OpenRouter). دابل‌دان مدل فقط از `model_allowlist` همان ارائه‌دهنده.
- همین‌جا افزودن/ویرایش/حذف ارائه‌دهنده هم در دسترس است (فرم ۱۳.۳).

### ۱۳.۴ نگاشت به Cline

| Cline | ما |
| --- | --- |
| «Use different models for Plan and Act Mode» | کلید «استفاده از یک ارائه‌دهنده برای هر دو بخش» (در پنل ⚙) |
| Plan Mode / Act Mode | «امور اداری» / «مدیریت» |
| API Provider dropdown | دابل‌دان ارائه‌دهنده در پنل ⚙ |
| API Key field | تکست‌باکس‌ها در صفحهٔ «ثبت کلیدها» |
| Model picker | دابل‌دان مدل در پنل ⚙ |
| پایگاه URL سفارشی | فیلد اختیاری `base_url` در فرم ارائه‌دهنده |

### ۱۳.۵ قواعد امنیتی و اعتبارسنجی (لازم‌الاجرا)

- هر POST با nonce از ماژول Crypto (نه `rand`/`mt_rand`)؛ همهٔ سقف‌ها و اعتبارسنجی‌ها در بک‌اند، نه فرانت (رفرش صفحه نمی‌تواند دورشان بزند).
- کلید API **فقط** رمزشده در مخزن کلیدِ پنل ذخیره می‌شود؛ لایهٔ ارائه‌دهنده فقط `keyRef` می‌گیرد و مقدار واقعی را فقط لبهٔ connector در لحظهٔ فراخوانی و یک‌بار حل می‌کند — هرگز در لاگ، DOM، اسکرین‌شات یا گزینهٔ وردپرس به‌صورت ساده نمی‌نشیند (هم‌راستا با `DESIGN-PADO` بند ۷۱۸/914 و `ADR-0004 §۳`).
- کلید خالی → «ثبت کلیدها» مسدود با پیام؛ ارائه‌دهنده بدون قابلیت موردنیاز بخش → هشدار `capability_unsupported` همان‌جا (نه بعد از ارسال).
- «تست اتصال» پس از ثبت = همان پروب سبک راستی‌آزمایی (یک پرامپت کوچک فارسی)، بدون انتشار یا اتصال واقعی.

### ۱۳.۶ رفتارهای لبه

- حذف ارائه‌دهنده‌ای که هنوز به یک بخش وصل است → مسدود تا بخش به ارائه‌دهندهٔ دیگر منتقل شود.
- تغییر ارائه‌دهندهٔ یک بخش → `model_allowlist` و مدل پیش‌فرض به مقادیر ارائه‌دهندهٔ جدید بازنشانی می‌شود.
- «یکسان برای هر دو بخش» روشن + بعداً خاموش → هر بخش به آخرین تنظیم جداگانه‌اش برمی‌گردد (بدون ازدست‌رفتن داده).
