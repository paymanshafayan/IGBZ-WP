**بازیابی:** ۱۴۰۵/۰۵/۳۱
**بازبینی وضعیت پروژه:** ۱۴۰۵/۰۶/۰۵، فاز ۰۱
**چرا در پروژهٔ ما:** مبنای قاعدهٔ ۵ در `PROJECT-STATE.md §۵.۵`، شکاف §۳ در
`DESIGN-GAPS-FIX.md` و نیازهای SEC-004/SEC-005 در `REQUIREMENTS-TRACEABILITY.md`.

---

## جدول ریسک

| بردار حمله | ضعف امنیتی | اثر |
|---|---|---|
| قابلیت بهره‌برداری: **متوسط** | شیوع: **گسترده** · قابل کشف: **آسان** | فنی: **شدید** |

بهره‌برداری فقط به درخواست‌های سادهٔ API نیاز دارد. درخواست‌های هم‌زمان متعدد را می‌شود از
یک کامپیوتر محلی یا با منابع ابری انجام داد.

**اثر:** هم DoS از راه تمام‌شدن منابع، و هم **افزایش هزینهٔ عملیاتی** (CPU بیشتر، فضای
ابری بیشتر).

---

## آیا API آسیب‌پذیر است؟

> پاسخ‌دادن به درخواست‌های API منابعی می‌خواهد: پهنای باند، CPU، حافظه، فضای ذخیره‌سازی.
> گاهی منابع لازم از راه یکپارچه‌سازی با ارائه‌دهنده‌ها تأمین می‌شوند و **هر درخواست پول
> دارد** — مثل ارسال ایمیل، **پیامک**، تماس تلفنی، و اعتبارسنجی بیومتریک.

API آسیب‌پذیر است اگر **دست‌کم یکی** از این محدودیت‌ها غایب یا نامناسب باشد:

- مهلت اجرا (Execution timeout)
- بیشینهٔ حافظهٔ قابل تخصیص
- بیشینهٔ تعداد توصیف‌گر فایل
- بیشینهٔ تعداد پروسه
- بیشینهٔ اندازهٔ فایل آپلودی
- تعداد عملیات در یک درخواست (مثل batching در GraphQL)
- **تعداد رکورد در هر صفحهٔ پاسخ**
- **سقف هزینهٔ ارائه‌دهندهٔ ثالث**

## 🔴 سناریوی #۱ — منشأ کشف شکاف تاریخی OTP

یک شبکهٔ اجتماعی جریان «فراموشی رمز» را با تأیید پیامکی پیاده کرد:

```
POST /initiate_forgot_password
{ "step": 1, "user_number": "6501113434" }
```

پشت صحنه، بک‌اند به سرویس پیامک ثالث درخواست می‌زند:

```
POST /sms/send_reset_pass_code
Host: willyo.net
{ "phone_number": "6501113434" }
```

ارائه‌دهنده بابت هر تماس **۰.۰۵ دلار** می‌گیرد.

> مهاجم اسکریپتی می‌نویسد که درخواست اول را **ده‌ها هزار بار** می‌فرستد. بک‌اند دنبالش
> می‌رود و ده‌ها هزار پیامک سفارش می‌دهد — **شرکت در عرض چند دقیقه هزاران دلار ضرر
> می‌کند.**

### ارتباط مستقیم با پروژهٔ ما

در snapshot نخست، `OtpService::send()` فقط بر اساس شماره محدود می‌شد و `ip_hash` در تصمیم
خوانده نمی‌شد. این شکاف بعداً با محدودیت ترکیبی شماره+IP و ایندکس متناظر اصلاح شد.

**وضعیت فاز ۰۱:** اصل کنترل در کد و تست حاضر است؛ بااین‌حال شمارندهٔ اتمیک زیر هم‌زمانی،
سهمیهٔ هزینهٔ پیامک، رفتار provider واقعی و پاسخ یکنواخت `429`/`Retry-After` هنوز مدرک
پذیرش کامل ندارند. جزئیات تاریخی: `DESIGN-GAPS-FIX.md §۳`؛ وضعیت جاری:
`REQUIREMENTS-TRACEABILITY.md` نیازهای SEC-004 و SEC-005.

## سناریوی #۲ — دور زدن محدودیت نرخ با batching

یک endpoint گرافیکی که بعد از آپلود عکس، بندانگشتی می‌سازد (مصرف حافظهٔ بالا). API هم
محدودیت نرخ سنتی دارد، هم اندازهٔ عکس را چک می‌کند.

ولی مهاجم با انعطاف GraphQL هر دو را دور می‌زند:

```
POST /graphql
[
  {"query": "mutation {uploadPic(name: \"pic1\", ...) {url}}"},
  {"query": "mutation {uploadPic(name: \"pic2\", ...) {url}}"},
  ...
  {"query": "mutation {uploadPic(name: \"pic999\", ...) {url}}"}
]
```

**درس برای ما:** محدودیت نرخِ «هر درخواست» کافی نیست وقتی یک درخواست می‌تواند صدها عملیات
داشته باشد. باید **تعداد عملیات داخل یک درخواست** هم محدود شود.

## سناریوی #۳ — هزینهٔ ابری بدون هشدار

فایلی از ۱۵GB (سقف کش) به ۱۸GB رسید. کش دیگر نگهش نداشت و همهٔ کلاینت‌ها مستقیم از ذخیره‌ساز
ابری کشیدند. چون **نه سقف هزینه بود نه هشدار**، صورتحساب ماهانه از میانگین ۱۳ دلار به
**۸۰۰۰ دلار** رسید.

---

## چطور جلوگیری کنیم (نقل مستقیم)

- استفاده از راهکاری که محدودکردن **حافظه، CPU، تعداد ری‌استارت، توصیف‌گر فایل و پروسه**
  را آسان کند — مثل کانتینر یا کد بدون‌سرور.
- تعریف و اعمال **بیشینهٔ اندازهٔ داده** روی همهٔ پارامترها و بدنه‌ها: طول رشته، تعداد
  عناصر آرایه، اندازهٔ فایل آپلودی.
- اعمال **محدودیت نرخ**: چند بار در بازهٔ زمانی مشخص.
- محدودیت نرخ باید **بر اساس نیاز کسب‌وکار تنظیم شود**؛ بعضی endpointها سیاست سخت‌گیرانه‌تر
  می‌خواهند.
- **محدودکردن تعداد دفعات اجرای یک عملیات خاص توسط یک کلاینت** — و صریحاً مثال می‌زند:
  «مثل **اعتبارسنجی OTP** یا درخواست بازیابی رمز».
- اعتبارسنجی سمت سرور برای پارامترهای query و بدنه، **مخصوصاً آنکه تعداد رکوردهای
  برگشتی را کنترل می‌کند**.
- **پیکربندی سقف هزینه** برای همهٔ ارائه‌دهنده‌ها. اگر سقف ممکن نیست، **هشدار صورتحساب**
  تنظیم شود.
