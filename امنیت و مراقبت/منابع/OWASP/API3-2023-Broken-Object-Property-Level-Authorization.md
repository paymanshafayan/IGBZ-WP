# API3:2023 — Broken Object Property Level Authorization

**منبع رسمی:** https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/
**بازیابی:** ۱۴۰۵/۰۵/۳۱
**ثبت محل استفاده:** ۱۴۰۵/۰۶/۰۵، فاز ۰۱
**چرا در پروژهٔ ما:** مبنای فهرست سفید ورودی/خروجی، منع mass assignment و کنترل مجوز
ویژگی در `DESIGN-LEGAL-AUTH.md §۷.۶/§۷.۷` و نیاز SEC-002 در

## این دسته از ادغام دو ریسک ۲۰۱۹ ساخته شده

| ۲۰۱۹ | ۲۰۲۳ |
|---|---|

| `API6` Mass Assignment | ← ادغام در `API3:2023` |

یعنی دو روی یک سکه: **خواندنِ** ویژگی‌هایی که نباید، و **نوشتنِ** ویژگی‌هایی که نباید.

## آیا API آسیب‌پذیر است؟

endpoint آسیب‌پذیر است اگر:

- ویژگی‌هایی از یک شیء را نمایش دهد که **حساس‌اند و کاربر نباید بخواندشان**
  (نام قبلی: Excessive Data Exposure)
- به کاربر اجازه دهد **مقدار ویژگی حساسی را تغییر دهد، اضافه یا حذف کند** که نباید
  دسترسی داشته باشد (نام قبلی: Mass Assignment)

## سناریوی #۲ — دستکاری قیمت (مرتبط با فروشگاه ما)

میزبان درخواست تأیید رزرو می‌فرستد:

```
POST /api/host/approve_booking
{ "approved": true, "comment": "Check-in is after 3pm" }
```

بعد همان درخواست را با یک فیلد اضافه بازپخش می‌کند:

```
{ "approved": true, "comment": "…", "total_stay_price": "$1,000,000" }
```

چون اعتبارسنجی نشده که میزبان به ویژگی داخلی `total_stay_price` دسترسی دارد یا نه، مهمان
مبلغ اشتباه شارژ می‌شود.

> **درس برای ما:** هر endpoint نوشتنی در ماژول‌های پرداخت، سفارش و کیف پول باید
> **فهرست سفید فیلد** داشته باشد. پذیرفتن کورکورانهٔ بدنهٔ درخواست = همین آسیب‌پذیری.

## سناریوی #۳ — دور زدن وضعیت داخلی

کاربر توضیح ویدیو را عوض می‌کند، ولی فیلد `blocked: false` را هم اضافه می‌کند و محتوای
مسدودشدهٔ خودش را آزاد می‌کند.

> **درس برای ما:** فیلدهای وضعیت داخلی (`status`, `verified`, `tenant_id`, `role`) هرگز
> نباید از بدنهٔ درخواست کاربر خوانده شوند.

## چطور جلوگیری کنیم (نقل مستقیم)

- هنگام نمایش یک شیء، **همیشه مطمئن شوید کاربر به ویژگی‌هایی که نمایش می‌دهید دسترسی
  دارد**.
- از متدهای عمومی مثل `to_json()` و `to_string()` **پرهیز کنید**؛ به‌جایش ویژگی‌های
  مشخصی را که می‌خواهید برگردانید **دستی انتخاب کنید**.
- تا حد ممکن از توابعی که ورودی کلاینت را **خودکار** به متغیرها یا ویژگی‌های شیء
  می‌بندند پرهیز کنید (Mass Assignment).
- فقط اجازهٔ تغییر ویژگی‌هایی را بدهید که کلاینت باید به‌روزشان کند.
- یک مکانیزم **اعتبارسنجی پاسخ بر پایهٔ شِما** به‌عنوان لایهٔ اضافی پیاده کنید.
- ساختار دادهٔ برگشتی را **به حداقلِ نیاز کسب‌وکار** محدود کنید.
