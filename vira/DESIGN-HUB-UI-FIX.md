## ۲.۵ 🔴 هاب کار نمی‌کند — تشخیص

کارفرما گزارش داد ویرا در حالت هاب خطا می‌دهد. کد را ممیزی کردم و **وضعیت تصویر کارفرما را
با اجرای واقعی بازتولید کردم** (۴ اتصال، ۵۳۲ مدل، هاب روشن). سه یافته:

### یافتهٔ ۱ — 🔴 باگ قطعی: هر درخواست دارای تصویر شکست می‌خورد

بازتولید شد:

```
مدل‌ها: 532 | hubReady: {"ok":true}
متن ساده:  نامزد=532  مسدود=0     ✅
با ابزار:  نامزد=532  مسدود=0     ✅
با تصویر:  نامزد=0    مسدود=532   ❌  دلیل: «بینایی ندارد»
```

**علت:** `router.js:71` هر مدلی را که `caps.vision` نداشته باشد رد می‌کند. `caps.vision` از
`inferCaps()` در `registry.js:17` می‌آید که فقط با یک **الگوی نام** حدس می‌زند
(`gpt-4o|claude|gemini|…`). هر مدلی که نامش در آن الگو نباشد — که اکثریت ۵۳۲ مدل است —
`vision:false` می‌گیرد. اگر هیچ‌کدام از مدل‌های روشن در الگو نباشند، **پیام «همهٔ مسیرها شکست
خوردند» ظاهر می‌شود** حتی وقتی همه‌چیز سالم است.

**بدتر:** `hubReady()` این حالت را «آماده» می‌خواند، پس نوار وضعیت **سبز** می‌ماند و
می‌گوید «هاب فعال است» در حالی که هر پیام تصویردار شکست می‌خورد. کاربر هیچ سرنخی ندارد.

**اصلاح پیشنهادی:**
1. وقتی **هیچ** مدلی `vision` ندارد ولی درخواست تصویر دارد، به‌جای «هیچ مدلی در دسترس
   نیست»، پیام صریح بدهد: «هیچ‌کدام از مدل‌های روشن بینایی ندارند — یک مدل بینا روشن کن یا
   قابلیت بینایی این مدل را دستی علامت بزن.»
2. در صفحهٔ مدل‌ها، `vision` **قابل تیک‌زدن دستی** شود (الان فقط حدسی است). مدل‌هایی مثل
   `gemini-3`, `gpt-5.1`, `llama-4` که الگو نمی‌شناسدشان، دستی درست می‌شوند.
3. الگوی `VISION` به‌روز شود.

### یافتهٔ ۲ — پیام خطا علت واقعی را پنهان می‌کند

بازتولید با کلید نامعتبر:

```
خطا: همهٔ مسیرها شکست خوردند. آخرین خطا: به api.openai.com وصل نشدم. | kind: network
```

سه علتِ کاملاً متفاوت — کلید غلط (۴۰۱)، تحریم جغرافیایی (۴۰۳)، پراکسی خاموش — همگی به
همین یک جملهٔ مبهم می‌رسند. `explain()` در `errors.js` `hint` تولید می‌کند اما در پیام
نهایی `stream()` (خط ۴۳۶) فقط `message` نمایش داده می‌شود و `hint` عملاً گم می‌شود.

**اصلاح:** پیام نهایی باید بگوید **چند مسیر آزموده شد، هرکدام چه داد، و گام بعدی چیست** —
با `hint` و لینک مستقیم به «تست اتصال» و «لاگ‌ها».

### یافتهٔ ۳ — ناسازگاری شناسه‌ها (جزئی)

`catalog.js:64` شناسهٔ گوگل را `google` گذاشته، ولی `hubpage.js:29` در نقشهٔ رنگ برند دنبال
`google-gemini` می‌گردد. اثرش فقط رنگ نادرست کارت است، نه شکست کارکرد — ولی همراه بقیه
اصلاح می‌شود.

### آنچه سالم بود

`hubReady()`، مسیریابی متن ساده و ابزاردار، مدارشکن، سقف روزانه، و انتخاب راهبرد همگی درست
کار می‌کنند. مشکل در **گیت بینایی** و **کیفیت پیام خطا** است، نه در معماری مسیریاب.

> **نکتهٔ صادقانه:** چون کلید واقعی ندارم، نمی‌توانم قطعی بگویم خطای *دستگاه شما* همین
> است. سه یافتهٔ بالا قطعی‌اند، ولی ممکن است علت اصلی چیز دیگری باشد (مثلاً پراکسی یا
> تحریم). برای همین **گام اول اجرا این است: از تنظیمات ← لاگ‌ها، متن دقیق خطا را بگیریم.**
> بخش لاگ‌ها در ۰.۹.۶ دقیقاً برای همین ساخته شد.

## ۲.۶ 🔴🔴 ریشهٔ واقعی پیدا شد: هاب پراکسی را دور می‌زند

سرنخ کارفرما (۱۴۰۵/۰۵/۳۰) کار را تمام کرد:

> «مشکل از آی‌پی ایران و پراکسی نیست، **چون در حالت تک‌واحد به‌خوبی کار می‌کند**.»

این جمله دقیقاً برعکسِ نتیجه‌گیری‌اش را ثابت می‌کند: **مشکل حتماً از پراکسی است، ولی نه از
تنظیمات شما — از کدِ ما.** دو مسیر را مقایسه کنید:

| | حالت تک‌واحد ✅ | حالت هاب ❌ |
|---|---|---|
| سازنده | `createProvider( profile )` — `providers/index.js:13` | `createConnectionProvider( conn, opts )` — خط ۷۶ |
| `cfg.proxy` | **اصلاً وجود ندارد!** | `conn.proxy \|\| opts.proxy` |
| نتیجه در `proxyFetch` | `proxy=undefined` → `dispatcherFor` مقدار `null` می‌دهد → **`fetch()` معمولی** | داسپچر پراکسی سوار می‌شود |

حالا کلید ماجرا در `net.js:103`:

```js
export async function proxyFetch( url, opts = {}, proxy = '' ) {
    const d = opts.dispatcher || dispatcherFor( url, proxy );
    if ( ! d ) { return fetch( url, opts ); }   // ← fetch سراسری Node
    return undiciFetch( url, { ...opts, dispatcher: d } );
}
```

**در حالت تک‌واحد `cfg.proxy` تعریف نشده، پس `d = null` و تماس با `fetch()` سراسری Node
می‌رود.** اگر کاربر ویرا را از ترمینالی اجرا کند که Hiddify متغیر `HTTPS_PROXY` را در آن
گذاشته — یا اگر Node نسخه‌ای باشد که پراکسی سیستم را می‌بیند — همان تماس **از تونل رد
می‌شود** و کار می‌کند.

**در حالت هاب، `conn.proxy` و `data.proxy.url` هر دو خالی‌اند** (کاربر در صفحهٔ پراکسی چیزی
پر نکرده، چون Hiddify کارش را می‌کرده). `normalizeProxy('')` رشتهٔ خالی می‌دهد، `d = null`
می‌شود و... **صبر کنید، این هم باید مثل تک‌واحد کار کند.** پس تفاوت کجاست؟

تفاوت در `effectiveProxy()` است (خط ۴۸): این تابع زنجیرهٔ درست را دارد
(`اتصال → هاب → محیط`) — **ولی `dispatcherFor` آن را صدا نمی‌زند.** فقط
`normalizeProxy( proxy )` را صدا می‌زند. یعنی:

- `envProxy()` (خواندن `HTTPS_PROXY`) **در مسیر واقعی هیچ‌وقت اجرا نمی‌شود**؛
- تابع `effectiveProxy` نوشته شده و **هیچ‌جا استفاده نمی‌شود** — کد مرده.

### نتیجه‌گیری

هر دو حالت پراکسی را دور می‌زنند، ولی **پیامدش برای هاب فاجعه‌بارتر است**:

- تک‌واحد: **یک** تماس به **یک** سرویس. اگر آن یکی تصادفاً باز باشد (یا Node پراکسی سیستم
  را ببیند)، کار می‌کند.
- هاب: پیش از هر پاسخ، **چند تماس** می‌زند (کشف مدل، تست، مسیریابی، failover روی چند
  اتصال). کافی است یکی تحریم بخورد تا نردبان failover همه را بیازماید و آخرش بگوید
  «همهٔ مسیرها شکست خوردند».

**اصلاح (سه خط):**

```js
// net.js — dispatcherFor باید از زنجیرهٔ کامل استفاده کند، نه فقط آرگومان
export function dispatcherFor( url, proxy, globalProxy = '' ) {
    const p = ( isLocalTarget( url ) || matchesException( url ) )
        ? '' : effectiveProxy( proxy, globalProxy );   // ← envProxy هم دیده می‌شود
    …
}
```

و در `providers/index.js:20` سازندهٔ تک‌واحد هم `proxy` بگیرد تا **هر دو حالت یک رفتار
داشته باشند**. امروز تک‌واحد از صفحهٔ پراکسیِ خود برنامه هیچ اطلاعی ندارد.

> این یافته **جای یافتهٔ «گیت بینایی» را نمی‌گیرد**؛ آن هم باگ واقعی است و بازتولید شد. ولی
> این یکی توضیح می‌دهد چرا **همهٔ** درخواست‌ها در حالت هاب شکست می‌خورند، نه فقط تصویردارها.

## ۲.۷ 🔴 تونل: چرا «هیچ کانفیگی اکتیو نیست» در حالی که در Hiddify کار می‌کنند

سؤال کارفرما: «کانفیگ‌های لودشده چطور تست می‌شوند؟» — کد را خواندم و **سه باگ** پیدا کردم.

### روش فعلی تست (`engine.js:114-152`)

برای هر کانفیگ: یک پورت آزاد → نوشتن کانفیگ موقت → `spawn(xray run -c …)` → **۳۵۰ms صبر**
→ `fetch('https://api.ipify.org?format=json')` از راه SOCKS محلی → مهلت کل **۸ ثانیه** →
کشتن پروسه.

### باگ ۱ — ۳۵۰ میلی‌ثانیه برای بالا آمدن xray کافی نیست

```js
await new Promise( ( r ) => setTimeout( r, 350 ) ); // فرصت بالا آمدن
```

روی ویندوز، xray برای خواندن کانفیگ، اتصال TLS/REALITY و آماده‌کردن inbound معمولاً
**۱ تا ۳ ثانیه** لازم دارد — مخصوصاً بار اول که Defender فایل را اسکن می‌کند. اگر `fetch`
زودتر برسد، `ECONNREFUSED` می‌گیرد و کانفیگِ **سالم**، «خراب» علامت می‌خورد.

**اصلاح:** به‌جای صبر ثابت، **پولینگ** روی پورت SOCKS تا وقتی جواب بدهد (هر ۱۵۰ms تا سقف
۵ ثانیه)، بعد تماس آزمایشی.

### باگ ۲ — `api.ipify.org` ممکن است خودش مسدود باشد

مقصد آزمون یک URL ثابت است. اگر ipify از آن سرور خارجی در دسترس نباشد (یا rate-limit
بخورد، یا DNS نگیرد)، **همهٔ کانفیگ‌ها یک‌جا شکست می‌خورند** — دقیقاً همان «هیچ‌کدام اکتیو
نیست». Hiddify از `cp.cloudflare.com/generate_204` استفاده می‌کند که سبک‌تر و مقاوم‌تر است.

**اصلاح:** چند مقصد جایگزین (`cp.cloudflare.com/generate_204`, `gstatic.com/generate_204`)
و شکست فقط وقتی **همه** رد شوند. ضمناً `204` بدنه ندارد، پس `res.json()` هم حذف می‌شود.

### باگ ۳ — پارس Shadowsocks خراب است (اثبات‌شده)

تابع `b64()` در `parse.js:6` همیشه `JSON.parse` می‌کند:

```js
function b64( s ) { … return JSON.parse( Buffer.from( … ).toString('utf8') ); … }
```

این برای `vmess://` درست است (محتوایش JSON است)، ولی برای `ss://` که محتوایش
`method:password` است **همیشه `null` برمی‌گرداند**. اجرا کردم:

```
ss cred base64: YWVzLTI1Ni1nY206bXlwYXNzd29yZA==
b64() روی آن -> null        ← پارس شکست خورد
```

نتیجه: **هر کانفیگ Shadowsocks که در شش منبع باشد، بی‌صدا دور ریخته می‌شود.**

**اصلاح:** جداکردن `b64Json()` از `b64Text()`.

### باگ ۴ — هم‌زمانی ۴ با مهلت ۸ ثانیه

`CONC = 4` با ۴۰۰ کانفیگ یعنی تا ۱۳ دقیقه. کاربر فکر می‌کند هنگ کرده. با اصلاح باگ ۱
(پولینگ به‌جای صبر ثابت) می‌شود هم‌زمانی را به ۸–۱۰ برد و مهلت را به ۶ ثانیه کم کرد.

### باگ ۵ — خطای هر کانفیگ به کاربر نشان داده نمی‌شود

`c.error` ذخیره می‌شود ولی در رابط فقط «سالم/ناسالم» دیده می‌شود. کاربر نمی‌فهمد
`timeout` بوده یا `ECONNREFUSED` یا خطای پارس.

**اصلاح:** ستون علت در جدول کانفیگ‌ها + خلاصهٔ دسته‌بندی‌شده («۱۲ مهلت، ۳ رد اتصال، ۴۰۰
پارس‌نشده»).

## ۲.۸ تست دومرحله‌ای با پرووایدر واقعی (خواستهٔ کارفرما ۱۴۰۵/۰۵/۳۰)

> «در تست کانفیگ‌ها، از طریق آن‌ها **یک پرووایدر فعال را تست کند** و در صورت اتصال موفق،
> کانفیگ را سالم اعلام کن. البته **بعد از تست اولیه**، که کانفیگ‌های غیرفعال را بی‌خود تست
> نگیرد.»

این خواسته یک نقص بنیادی را می‌بندد. امروز کانفیگ با `api.ipify.org` سنجیده می‌شود — یعنی
جواب می‌دهد به سؤال **«آیا این تونل به اینترنت وصل است؟»**، نه به سؤالی که واقعاً مهم است:
**«آیا از این تونل می‌شود به OpenAI رسید؟»** این دو یکی نیستند: بسیاری از سرورهای رایگان
اینترنت عمومی می‌دهند ولی خودشان از سمت OpenAI/Anthropic **مسدود** یا geo-block اند. پس
کانفیگ «سالم» علامت می‌خورد و بعد هاب با آن شکست می‌خورد — دقیقاً تجربهٔ کارفرما.

### طرح: دو مرحله، و مرحلهٔ دوم فقط روی بازمانده‌ها

| | مرحله ۱ — غربال سریع | مرحله ۲ — تأیید واقعی |
|---|---|---|
| هدف | آیا تونل اصلاً بالا می‌آید؟ | آیا **پرووایدر واقعی** از این تونل جواب می‌دهد؟ |
| مقصد | `generate_204` (سبک، چند جایگزین) | `GET {baseUrl}/models` روی یک اتصال **فعالِ** هاب |
| روی چه کسی | همهٔ کانفیگ‌های `enabled` | **فقط آن‌هایی که مرحلهٔ ۱ را رد کردند** |
| مهلت | ۶ ثانیه | ۱۲ ثانیه |
| هم‌زمانی | ۸ | ۳ (مهربان با سرویس‌دهنده) |
| نتیجه | `ok1` | **`ok` نهایی** |

**«بعد از تست اولیه» دقیقاً همین است:** کانفیگی که در مرحلهٔ ۱ افتاده، وارد مرحلهٔ ۲
نمی‌شود. با ۴۰۰ کانفیگ که مثلاً ۶۰ تایشان زنده‌اند، به‌جای ۴۰۰ تماس سنگین به OpenAI فقط
۶۰ تا زده می‌شود — هم سریع‌تر، هم بی‌احترامی به سرویس‌دهنده نیست، هم ریسک rate-limit کم است.

### کدام پرووایدر برای مرحلهٔ ۲؟

انتخاب خودکار، به این ترتیب:

1. اتصالی که کاربر در صفحهٔ تونل **سنجاق** کرده (گزینهٔ تازه: «سرویس معیار»)؛
2. وگرنه نخستین اتصال هاب که `enabled` است و کلید دارد؛
3. اگر هیچ اتصالی نبود، مرحلهٔ ۲ **رد می‌شود** (نه اینکه شکست بخورد) و کانفیگ با نشان
   «فقط اینترنت — با سرویس آزموده نشد» می‌ماند. کاربر بدون اتصال نباید بن‌بست بخورد.

**فقط `GET /models` زده می‌شود** — بی‌هزینه، بدون توکن، و کافی است چون هم TLS، هم مسیر، هم
پذیرش IP را با هم می‌سنجد. هیچ درخواست تکمیل (chat) زده نمی‌شود که پول خرج کند.

**تفکیک ۴۰۱ از تحریم — ظرافت مهم:** اگر پاسخ **۴۰۱/۴۰۳ با بدنهٔ JSON خود سرویس** باشد،
یعنی **تونل سالم است** و فقط کلید مشکل دارد → کانفیگ **سالم** علامت می‌خورد. تنها خطای
شبکه/DNS/timeout یا ۴۰۳ـِ لبهٔ CDN، کانفیگ را ناسالم می‌کند. بدون این تفکیک، کلیدِ غلطِ
کاربر باعث می‌شود همهٔ کانفیگ‌های خوب دور ریخته شوند.

### وضعیت سه‌حالته در انبار

هر کانفیگ به‌جای `ok: boolean` سه حالت می‌گیرد:

| نشان | معنی |
|---|---|
| ✅ **سالم** | مرحلهٔ ۱ و ۲ هر دو موفق — به سرویس واقعی می‌رسد |
| 🟡 **فقط اینترنت** | مرحلهٔ ۱ موفق، مرحلهٔ ۲ ناموفق (سرویس مسدود است) |
| ❌ **خراب** | مرحلهٔ ۱ ناموفق |

`pickBest()` اول از ✅ ها انتخاب می‌کند و فقط اگر هیچ ✅ ای نبود سراغ 🟡 می‌رود.

## ۲.۹ نمایش پیشرفت — کاربر باید بفهمد کار در جریان است

> «در زمان تست کانفیگ‌ها و لود روی xray، با یک **آیکون لودر یا پروگرس‌بار** وضعیت انتظار را
> نمایش بده تا کاربر متوجه شود کار در حال انجام است.»

**وضعیت امروز — و یک یافتهٔ عجیب:** بک‌اند از قبل پیشرفت را می‌فرستد!
`server.js:477` روی هر کانفیگ `broadcast({ type:'tunnel', progress:{ done, total, name, ok, ms } })`
می‌زند. اما **رابط اصلاً به آن گوش نمی‌دهد** — در کل `ui/proxy.js` حتی یک بار کلمهٔ
`progress` نیامده. کاربر یک toast می‌بیند («چند دقیقه ممکن است بشود…») و بعد **تا ۱۳ دقیقه
سکوت مطلق**، و در این مدت پنجره هم بسته/باز شود همه‌چیز گم می‌شود.

پس این بخش عمدتاً **وصل‌کردن چیزی است که از قبل ساخته شده**، نه ساختن از صفر.

### آنچه اضافه می‌شود

**۱) نوار پیشرفت واقعی برای «تست همه»** — با درصد، شمارش، و نام کانفیگ در حال آزمون:

```
تست کانفیگ‌ها  ▓▓▓▓▓▓▓░░░░░░░  ۸۷ از ۲۴۰   ·  ✅ ۱۲ سالم  🟡 ۵  ❌ ۷۰
اکنون: Germany-Frankfurt-03  (مرحلهٔ ۲ — آزمون OpenAI)
```

نوار **مرحله را هم نشان می‌دهد** («غربال سریع» / «آزمون سرویس») چون مرحلهٔ ۲ کندتر است و
بدون توضیح، کاربر فکر می‌کند گیر کرده.

**۲) اسپینر روی کارهای بدون درصد** — «دانلود هسته»، «روشن‌کردن تونل»، «چرخش». اینها طول
نامعلوم دارند، پس اسپینر داخل خود دکمه + متن «در حال…» و غیرفعال‌شدن دکمه.

**۳) دکمهٔ لغو.** کاری که چند دقیقه طول می‌کشد باید قابل توقف باشد. `testAll` یک پرچم
`cancelled` می‌گیرد که بین کانفیگ‌ها چک می‌شود؛ نتایج تا آن لحظه ذخیره می‌شوند.

**۴) پایداری در برابر بستن پنجره.** پیشرفت در وضعیت موتور (`S.testing = {done,total,phase}`)
نگه داشته می‌شود و `GET /api/tunnel` آن را برمی‌گرداند، تا اگر کاربر صفحه را ببندد و برگردد،
نوار همان‌جا که بود ادامه پیدا کند.

**۵) هماهنگی با بقیهٔ رابط.** از همان `.steps` و کلاس‌های موجود استفاده می‌شود و رشته‌ها از
مسیر `data-t` می‌گذرند تا دوزبانگی نشکند.

> **نکتهٔ مهم:** این پنج مورد قطعی‌اند، ولی چون سندباکس من به اینترنت آزاد و به xray دسترسی
> ندارد، **نمی‌توانم تست تونل را سر تا سر بازتولید کنم**. تأیید نهایی روی دستگاه شماست.

## ۲.۱۰ سه ایراد نهایی کارفرما (۱۴۰۵/۰۵/۳۰) — خارج از صفحهٔ هاب

این سه، به صفحهٔ هاب ربطی ندارند ولی چون ایرادات نهایی همین دورند، اینجا ثبت و با هم اجرا
می‌شوند.

### ۲.۱۰.۱ دکمهٔ «رفتن به پایین» تا اسکرول نکنی ظاهر نمی‌شود

**ریشه — `thread.js:32-49`:** دکمه با `hidden: true` ساخته می‌شود و تنها جایی که این مقدار
عوض می‌شود، **داخل شنوندهٔ `scroll`** است:

```js
const jump = h( 'button', { …, hidden: true, … } );
chat.addEventListener( 'scroll', () => { jump.hidden = atBottom(); } );
```

تا کاربر دست به اسکرول نزند، آن شنونده **هرگز اجرا نمی‌شود**. پس در پرمصرف‌ترین حالت —
پاسخ بلندی که خودش صفحه را پر می‌کند و کاربر هنوز اسکرول نکرده — دکمه پنهان می‌ماند.
دقیقاً وقتی که بیشترین کاربرد را دارد.

**اصلاح:** وضعیت دکمه یک تابع مستقل (`syncJump()`) شود که در سه جای دیگر هم صدا زده شود:
۱. یک بار در `mountThread` (وضعیت اولیه)؛
۲. در `append()` — یعنی هر بار محتوای تازه‌ای به نخ اضافه می‌شود (استریم پاسخ)؛
۳. روی `ResizeObserver` نخ گفتگو — وقتی بلوک استدلال باز/بسته می‌شود یا پنجره عوض می‌شود.

### ۲.۱۰.۲ حذف توضیح فنی از رابط

**ریشه — `ui/proxy.js:83`:**

> «Node.js پراکسی سیستم را نمی‌بیند؛ تماس‌های پرووایدر از مسیر انتخابی این‌جا می‌گذرند.
> مقصدهای استثناشده همیشه مستقیم می‌مانند.»

این جمله **علتِ پیاده‌سازی** را به کاربر می‌گوید، نه کاری که باید بکند. کاربر لازم نیست
بداند Node چه می‌بیند و چه نمی‌بیند؛ این حرفِ سند طراحی است، نه حرفِ رابط.

**اصلاح:** حذف کامل آن `<p class="note">` از `proxy.js` و حذف کلید متناظرش از
`ui/lib/i18n.js:50` تا ترجمهٔ یتیم نماند. زیرِ عنوان «پراکسی» چیزی جایگزینش نمی‌شود —
خودِ فیلدها گویا هستند. توضیح فنی به کامنت کد و همین سند منتقل می‌شود.

> **بازبینی هم‌خانواده‌ها:** موقع اجرا، بقیهٔ `note`های همان صفحه هم با همین معیار سنجیده
> می‌شوند («آیا به کاربر می‌گوید چه کند، یا فقط توضیح می‌دهد چرا کد این‌طور نوشته شده؟»).
> نمونهٔ مشکوک: بند بلند «مثل یک v2ray داخل ویرا…» در خط ۲۰۸. هرچه فقط توضیح فنی است
> کوتاه یا حذف می‌شود — ولی **هشدارهای ایمنی** (مثل «کانفیگ رایگان یعنی اپراتور ناشناس»)
> می‌مانند، چون آن‌ها تصمیم کاربر را عوض می‌کنند.

### ۲.۱۰.۳ باکس استدلال: نه پنجرهٔ ۴–۵ خطی، نه محو، نه حذف

خواستهٔ اصلی: **۴–۵ خط نمایش · با هر خط تازه، خط بالایی محو شود · پیش از رسیدن جواب، کل
باکس از صفحه برود.** کارفرما می‌گوید هیچ‌کدام کار نمی‌کند. کد را خواندم — و ماجرا از یک
باگ ساده جالب‌تر است:

**سه جزء از چهار جزء «به‌نظر» درست‌اند:**

| جزء | وضعیت در کد | حکم |
|---|---|---|
| ارتفاع ۵ خط | `line-height:1.6` + `max-height:8em` → دقیقاً ۵ خط | ✅ ریاضی درست |
| محوشدگی بالا | `.thinking-view::before` گرادیان ۱۲px | ⚠️ هست ولی ناکافی |
| اسکرول به آخر | `_body.scrollTop = _body.scrollHeight` | ❌ **بی‌اثر** |
| حذف پیش از جواب | `dropThinking()` در `case 'text'` و `assistant_end` | ⚠️ ناقص |

**باگ اصلی — اسکرول روی المان اشتباه:** `max-height: 8em` با **`overflow: hidden`** آمده،
نه `overflow-y: auto`. المانی که `overflow:hidden` دارد `scrollHeight > clientHeight` دارد
ولی **`scrollTop` رویش عملاً کار نمی‌کند** (مرورگر اجازهٔ اسکرول برنامه‌ای می‌دهد اما هیچ
نوار اسکرولی نیست و در عمل روی محتوای در حال رشد قابل اتکا نیست). نتیجه: متن استدلال از
بالا ثابت می‌ماند و **۵ خط اولش** دیده می‌شود، نه ۵ خط آخر. کاربر فکر می‌کند «هیچ‌کدام کار
نمی‌کند» چون دقیقاً برعکسِ خواسته رفتار می‌کند: خط‌های **قدیمی** می‌مانند و تازه‌ها پنهان‌اند.

**اصلاح:** به‌جای دستکاری `scrollTop` روی جعبهٔ مخفی، از چیدمان معکوس استفاده شود —
`.thinking-body { display:flex; flex-direction:column-reverse; overflow:hidden }` با متن در
یک `<span>` داخلش، یا ساده‌تر: نگه‌داشتن متن در آرایه و رندر **فقط ۵ خط آخر**. راه دوم
قطعی‌تر است چون به رفتار اسکرول مرورگر وابسته نیست:

```js
thinkEl._lines.push( …ev.text.split('\n') );
thinkEl._body.textContent = thinkEl._lines.slice( -5 ).join('\n');
```

**محوشدگی واقعی:** گرادیان فعلی روی `.thinking-view` است ولی `.thinking-body` **فرزند**
آن است و رنگ پس‌زمینه‌اش را نمی‌گیرد؛ ضمناً ۱۲px برای یک خط ۱.۶em (~۲۲px) کم است. با رندرِ
«۵ خط آخر»، محو باید روی **خط اول همان پنجره** بیفتد: ارتفاع گرادیان به ~۱.۶em می‌رسد و
`opacity` خط اول با یک ترنزیشن کوتاه کم می‌شود تا حس «محوشدن خط بالایی» واقعاً دیده شود.

**حذف پیش از جواب — سوراخ واقعی:** `dropThinking()` در `case 'text'` و `assistant_end` صدا
زده می‌شود، ولی **در مسیر ابزار نه**. اگر مدل استدلال کند و بعد به‌جای متن یک ابزار صدا بزند
(`tool_start`)، باکس استدلال سر جایش می‌ماند و روی کارت ابزار سوار می‌شود — و اگر آن نوبت
هیچ‌وقت به `text` نرسد، تا پایان گفتگو می‌ماند. **این همان «حذف نمی‌شود»ی است که کارفرما
دید.** اصلاح: `dropThinking()` به `tool_start` و `permission_request` هم اضافه شود.

## ۳. یال‌های توپولوژی — خواستهٔ صریح کارفرما

### ۳.۱ آنچه کارفرما گفت

> «یال‌ها سه وضعیت دارند: active / recent / error. در **recent** و **error** یال‌ها به شکل
> **خط ممتد** و به **همان رنگ** وضعیت نمایش داده می‌شوند. در **active** یال‌ها به شکل
> **نقطه‌چین سبز متحرک** که نقطه‌ها **به سمت پرووایدرها در حرکت‌اند**.»

### ۳.۲ تعریف سه وضعیت

| وضعیت | معنی | شکل یال | رنگ |
|---|---|---|---|
| **active** | همین حالا در حال استفاده / تازه‌کار (پنجرهٔ ۶۰ ثانیه) | **نقطه‌چین متحرک**، جهت: مرکز ← پرووایدر | سبز `--ok` |
| **recent** | در پنجرهٔ اخیر کار کرده ولی الان نه (پیش‌فرض ۱۵ دقیقه) | خط **ممتد** | کهربایی `#d9a441` |
| **error** | آخرین نتیجه خطا بود، یا مدار باز، یا اعتبار تمام | خط **ممتد** | قرمز `--destructive` |
| *(بی‌حالت)* | هرگز استفاده نشده یا خاموش | خط ممتد کم‌رنگ | `--border` |

**سه وضعیت اول دقیقاً همان راهنمای بالا-راست Snap10 است** (`Active` سبز · `Recent` کهربایی ·
`Error` قرمز) و راهنما هم باید همان‌جا و با همان ترتیب گذاشته شود.

### ۳.۳ داده‌ای که کم است — یک تغییر کوچک در بک‌اند

`health.js` همین حالا `e.lastUsedAt` را نگه می‌دارد (خط ۷۴) **ولی در `snapshot()` بیرون
نمی‌دهد** (خط ۲۳۴–۲۵۲). بدون این عدد، تفکیک active از recent ممکن نیست.

```js
// src/hub/health.js — داخل snapshot()، دو کلید اضافه:
lastUsedAt: e.lastUsedAt || 0,
lastOk:     Boolean( e.lastOk ),
```

`lastOk` هم اضافه می‌شود چون «آخرین نتیجه خطا بود» با `fail > 0` قابل تشخیص نیست (یک
شکستِ قدیمی که بعدش ده موفقیت آمده، خطا نیست). در `record()` یک خط:
`e.lastOk = Boolean( result.ok );`

این تنها تغییر منطقی بک‌اند در کل این پلن است. **هیچ رفتار مسیریابی‌ای عوض نمی‌شود.**

### ۳.۴ چرا SVG جایگزین div می‌شود

پیاده‌سازی فعلی هر یال را یک `div` چرخانده با `rotate()` می‌سازد (`hubpage.js:236-244`).
با این روش **نقطه‌چین متحرکِ جهت‌دار غیرممکن است**. راه درست `<svg>` با `<line>` و
`stroke-dasharray` + انیمیشن روی `stroke-dashoffset` است:

```css
.topo-edge.active {
    stroke: var(--ok);
    stroke-width: 2;
    stroke-dasharray: 2 7;        /* نقطه، نه خط‌چین */
    stroke-linecap: round;
    animation: topo-flow 1.1s linear infinite;
}
@keyframes topo-flow {
    to { stroke-dashoffset: -9; }  /* = مجموع dasharray؛ حلقهٔ بی‌درز */
}
.topo-edge.recent { stroke: #d9a441; stroke-width: 2; }
.topo-edge.error  { stroke: var(--destructive); stroke-width: 2; }
.topo-edge.idle   { stroke: var(--border); stroke-width: 1.5; }
```

**جهت حرکت** با ترتیب مختصات تضمین می‌شود: هر `<line>` از **مرکز** (`x1,y1` = هاب) به
**پرووایدر** (`x2,y2`) کشیده می‌شود، و `stroke-dashoffset` منفی می‌شود — پس نقطه‌ها از هاب
به سمت پرووایدر می‌روند، همان‌طور که کارفرما خواست.

> ⚠️ **تلهٔ RTL:** رابط `dir="rtl"` است. مختصات SVG از RTL تأثیر نمی‌گیرد ولی اگر روی ظرفِ
> SVG `transform: scaleX(-1)` یا جهت‌دهی ارثی بیفتد، جهت نقطه‌ها برعکس می‌شود. ظرف صریحاً
> `direction: ltr` می‌گیرد و بعد از پیاده‌سازی **چشمی** بررسی می‌شود.

### ۳.۵ گره‌ها: مستطیل‌های کوچک (خواستهٔ صریح کارفرما)

> «برای نمایش پرووایدرها مانند تصویر OmniRoute از **مستطیل‌های کوچک** استفاده کن، برای
> زمانی که تعداد پرووایدرها زیاد باشد.»

در Snap10 هر پرووایدر یک **قرص کوچک افقی** است: آیکون ریز + نام در یک خط + یک نقطهٔ وضعیت،
با ارتفاع ~۲۶px. گره فعلی ویرا یک کارت عمودی سه‌طبقه است (نام، «۱۱۸ مدل · فعال»، و گاهی
دکمهٔ «ریست و رفع خطا») با `min-width:96px` و ارتفاع ~۷۰px — یعنی **حدود سه برابر** مرجع.
با ۱۰ پرووایدر روی هم می‌افتند.

**تغییر:**

| ویژگی | حالا | بعد |
|---|---|---|
| شکل | کارت عمودی ۳ طبقه | **مستطیل افقی تک‌خطه** |
| ارتفاع | ~۷۰px | **۲۶–۲۸px** |
| محتوا | نام + شمار مدل + وضعیت + دکمه | نقطهٔ وضعیت + آیکون + نام |
| شمار مدل | داخل گره | در **tooltip** |
| دکمهٔ ریست | داخل گره | حذف — با کلیک به صفحهٔ جزئیات |
| نام بلند | می‌شکند | `text-overflow: ellipsis` با سقف ~۱۴ch |

دکمهٔ «ریست و رفع خطا» از داخل گره برداشته می‌شود: هم گره را بزرگ می‌کند، هم روی نقشه جای
درستی نیست. کلیک روی گره ← صفحهٔ جزئیات همان سرویس، که دکمه آنجا هست.

**چیدمان برای تعداد زیاد:** چیدمان دایره‌ای فعلی با `R = min(W,H)/2 - 70` تا ~۸ گره خوب است.
برای بیشتر، **دو حلقهٔ هم‌مرکز** (۸ تای اول داخلی، بقیه بیرونی) تا گره‌ها روی هم نیفتند.
بوم هم از ۶۴۰×۳۶۰ ثابت به **واکنش‌گرا** تبدیل می‌شود (`viewBox` + `width:100%`) تا از عرضِ
آزادشدهٔ §۴ استفاده کند.

### ۳.۶ احترام به `prefers-reduced-motion`

فایل CSS در خط ۱۹۶۵ یک بلوک `prefers-reduced-motion` دارد که همهٔ انیمیشن‌ها را به
`0.01ms` می‌برد. برای یال active این یعنی نقطه‌ها **منجمد** می‌شوند و کاربر تفاوت active و
recent را نمی‌فهمد. پس یک استثنا لازم است: در حالت کاهش حرکت، یال active به‌جای انیمیشن،
`stroke-dasharray` را نگه می‌دارد و یک نشانگر ثابت (مثلث کوچک جهت‌نما وسط یال) می‌گیرد.

## ۴. اصلاح ۱ — آزادکردن عرض (مهم‌ترین تغییر)

مشکل: `#panel-body` همیشه کلاس `.page-inner` دارد (`index.html:224`) و آن کلاس
`max-width: 56rem` می‌گذارد. صفحهٔ هاب که باید تمام‌قد باشد هم داخل همین می‌افتد.

راه‌حل — یک کلاس مودال‌کننده روی همان ظرف، بدون دست‌زدن به بقیهٔ صفحه‌ها:

```css
.page-inner.wide {
    max-width: min( 1600px, 100% );
    padding: 32px 40px;
}
```

و در `app.js` هنگام نشان‌دادن صفحهٔ `hub`، کلاس `wide` روی `#panel-body` گذاشته و هنگام
خروج برداشته می‌شود. **صفحه‌های دیگر (گفتگوها، پروژه‌ها، ابزارها، تغییرات، فضای کار)
دست‌نخورده می‌مانند** — عرض ۵۶rem برای متن‌خوانی درست است و عوض نمی‌شود.

`padding` عمودی هم از ۶۴px به ۳۲px می‌آید؛ داشبورد نباید نصف صفحهٔ اول را حاشیه بدهد.

## ۵. اصلاح ۲ — یک لایه ناوبری، نه دو تا

مرجع (Snap4/10/11) یک سایدبار سراسری دارد و نماها آیتم‌های همان‌اند. در ویرا سایدبار اصلی
راست است و نباید شلوغ شود، پس **راه میانه**:

`.hub-side` (ستون عمودی) حذف و جایش یک **نوار تب افقی** زیر عنوان صفحه می‌نشیند — همان
الگویی که Snap5 برای `All / Intelligent / Deterministic` دارد. با این کار:

- ستون شناور وسط صفحه از بین می‌رود؛
- ۱۶۸px عرض به محتوا برمی‌گردد؛
- کاربر یک لایه ناوبری می‌بیند نه دو تا.

تب‌ها شمارنده هم می‌گیرند: `اتصال‌ها ۴` · `ترکیب‌ها ۰` — مثل مرجع.

## ۱۱. تست — سبک، طبق قاعدهٔ کارفرما

قاعدهٔ ۱۴۰۵/۰۵/۲۸: برای تغییر در ویرا **تست فراگیر گرفته نمی‌شود**؛ چند تست نرمال که نشان
دهد تغییر اعمال شده کافی است و کارفرما خودش کامل می‌آزماید. پس:

0. **`dispatcherFor` پراکسی محیط را می‌بیند** و هر دو حالت (تک‌واحد/هاب) یک رفتار دارند (۰آ).
0.5 **`b64Text` کانفیگ ss را درست پارس می‌کند** — همان نمونه‌ای که الان `null` می‌دهد (۰ج).
0.6 **مرحلهٔ ۲ فقط روی بازماندگان مرحلهٔ ۱ اجرا می‌شود** — با ۵ کانفیگ ساختگی که ۲ تایشان
    مرحلهٔ ۱ را رد می‌کنند، شمار تماس‌های مرحلهٔ ۲ باید دقیقاً ۲ باشد (۰د).
0.7 **۴۰۱ از سرویس، کانفیگ را سالم نگه می‌دارد** ولی timeout ناسالمش می‌کند (۰د).
0.8 **باکس استدلال فقط ۵ خط آخر را نگه می‌دارد** و با `tool_start` حذف می‌شود (۰ح).
0.9 **جملهٔ Node.js نه در `proxy.js` هست نه در `i18n.js`** (۰ز) — یک grep ساده.
1. **درخواست تصویردار وقتی هیچ مدل بینایی روشن نیست، پیام صریح می‌دهد** (باگ ۰).
2. یال‌ها سه کلاس درست را می‌گیرند (active/recent/error) بر اساس `lastUsedAt` و `lastOk`.
3. `snapshot()` دو کلید تازه را برمی‌گرداند.
4. صفحهٔ هاب کلاس `wide` را می‌گیرد و صفحهٔ گفتگوها نمی‌گیرد.

همین چهار تا. **سوئیت کامل ۳۷۵تایی اجرا نمی‌شود** مگر یک بار در پایان برای اطمینان از
نشکستن.

**تأیید زنده:** رابط بالا می‌آید، صفحهٔ هاب باز می‌شود، و از نمای توپولوژی **اسکرین‌شات
گرفته و با Snap10 مقایسه می‌شود** — این بار چشمی، نه از روی متن. گره‌ها با ۱۲ پرووایدر
ساختگی آزموده می‌شوند تا مطمئن شویم روی هم نمی‌افتند.

## ۱۵. گزارش اجرا (۰.۹.۷ — ۱۴۰۵/۰۵/۳۰)

همهٔ بندها یک‌جا پیاده شدند. آنچه در عمل فرق کرد یا تازه پیدا شد:

### ۱۵.۱ ریشهٔ اصلی تأیید شد — با جهش

`dispatcherFor` حالا `effectiveProxy` را صدا می‌زند. برای اطمینان از اینکه اصلاح واقعی
است نه ظاهری، کد عمداً به شکل قبلی برگردانده شد: با `normalizeProxy`، متغیر `HTTPS_PROXY`
نادیده می‌ماند و داسپچر `null` می‌شود — **همان باگ**. با اصلاح، پراکسی دیده می‌شود.

`createProvider` (تک‌واحد) هم `proxy` گرفت و `runtime` آن را از `hub.data.proxy.url`
پاس می‌دهد. حالا هر دو حالت یک زنجیره دارند.

### ۱۵.۲ سه چیز که فقط در اجرا معلوم شد

۱. **`querySelectorAll` روی SVG کار نمی‌کرد.** عناصر SVG کلاسشان را با
   `setAttribute('class', …)` می‌گیرند، ولی دابلِ DOM فقط `className` را می‌شناخت. تست
   «هر اتصال یک یال» صفر می‌داد در حالی که یال‌ها ساخته شده بودند. `setAttribute` در
   `test/fake-dom.mjs` اصلاح شد تا `class` را هم به `className` بنشاند.
۲. **`createElementNS` در دابل نبود** — سوئیت با `TypeError` می‌افتاد. اضافه شد.
۳. **دو تست، رفتار باگ‌دار را قفل کرده بودند.** یکی صریحاً
   `_body.scrollTop = _body.scrollHeight` را در متن فایل می‌طلبید — یعنی همان روشی که
   کار نمی‌کرد. دیگری دکمهٔ «ریست» را داخل گرهٔ توپولوژی می‌خواست. هر دو با خودِ خواستهٔ
   کارفرما بازنویسی شدند: «۵ خط آخر رندر شود» و «گره تمیز بماند، کلیک به جزئیات ببرد».
   این نمونهٔ خوبی است از تستی که «سبز بودن» را تضمین می‌کند نه «درست بودن» را.

### ۱۵.۳ ترجمهٔ رشته‌های تازه

تست «انگلیسی بدون ته‌ماندهٔ فارسی» متن راهنمای توپولوژی را گرفت. نکتهٔ ظریف: «فعال» از
قبل به `Enabled` نگاشت داشت، ولی در راهنمای یال معنی `Active` می‌دهد؛ و «اخیر» هم به
`Recents` (منوی نشست‌ها) نگاشت داشت. برای همین کلیدهای متمایز `اخیر (یال)` و
`خطا (یال)` ساخته شد تا نگاشت‌های موجود خراب نشوند.

| سوئیت | پیش از کار | پس از کار |
|---|---|---|
| واحد | ۳۷۵ موفق / ۱ محیطی | **۳۷۵ موفق / ۱ محیطی** (همان تست داکر) |

### ۱۵.۵ آنچه در سندباکس قابل تأیید نبود

- **نقطه‌چین متحرک و ظاهر نهایی نقشه:** منطق و CSS تأیید شد و هر ۷ حالت یال درست
  محاسبه می‌شود، ولی حرکت واقعی نقطه‌ها را باید روی مرورگر دید. برای همین ۱۰ اتصال

  «مرحلهٔ ۲ فقط روی بازماندگان» و تفکیک ۴۰۱ از تحریم در کد هست، ولی اجرای واقعی روی
  دستگاه کارفرماست.
- **رفع نهایی «هاب کار نمی‌کند»:** ریشه پیدا و اصلاح شد، ولی تأیید قطعی با کلید و شبکهٔ
  واقعی ممکن است.

## ۱۶. دور دوم (۱۴۰۵/۰۵/۳۰ شب) — چرا دور اول کافی نبود

کارفرما پس از تحویل ۰.۹.۷ گزارش داد: «فقط دکمهٔ رفتن به انتها درست شده.» بازبینی نشان داد
**تشخیص دور اول درست بود ولی ناقص** — سه باگ عمیق‌تر زیرش بود که با خواندن کد پیدا نمی‌شد و
فقط با **اجرای واقعی** بیرون آمد.

### ۱۶.۱ 🔴🔴 دو باگ کشنده در یک خط — علت واقعی «هیچ کانفیگ سالمی نیست»

```js
// کد ۰.۹.۶ و ۰.۹.۷ اول
const res = await fetch( url, {
    dispatcher: socksDispatcher( { url: new URL( `socks5://127.0.0.1:${port}` ) } ),
} );
```

با اجرای واقعی، **دو** خطای متفاوت بیرون آمد:

| # | خطا | علت |
|---|---|---|
| ۱ | `invalid onRequestStart method` | `fetch` سراسری Node داسپچرِ بستهٔ npm را نمی‌پذیرد |
| ۲ | `Invalid SOCKS proxy details were provided` | `socksDispatcher` آبجکت `{type,host,port}` می‌خواهد، نه `{url}` |

نکتهٔ تلخ: کامنت خودِ `net.js` باگ اول را از ۰.۹.۵ **می‌دانست و توضیح داده بود** — ولی
`tunnel/engine.js` همچنان `fetch` سراسری را صدا می‌زد. یعنی مستندات درست بود و کد از آن
پیروی نمی‌کرد.

**نتیجه:** تست تونل **صددرصد** شکست می‌خورد، صرف‌نظر از اینکه سرور سالم باشد یا نه. هیچ
کانفیگی هرگز نمی‌توانست «سالم» شود. اصلاحات دور اول (پولینگ، چند مقصد، پارس ss) همگی درست
بودند ولی پشت این دیوار بی‌اثر ماندند.

**باگ ۲ در `net.js` هم بود** (خط ۱۰۱) — یعنی هر پراکسی `socks5://` در خود هاب هم بی‌صدا
شکست می‌خورد. Hiddify معمولاً socks5 می‌دهد.

### ۱۶.۲ 🔴 پراکسی در بوت روی هاب نمی‌نشست

`syncProxyToHub()` فقط از مسیرهای `/api/proxy` و `/api/tunnel` صدا زده می‌شد — یعنی تنها
وقتی کاربر صفحهٔ پراکسی را باز می‌کرد. **با هر بار بستن و باز کردن برنامه،
`hub.data.proxy.url` خالی می‌ماند** و تماس‌های هاب مستقیم می‌رفتند → ۴۲۹ «درخواست‌ها زیاد
است» (Snap23). حالا در بوت هم اعمال می‌شود.

### ۱۶.۳ باکس‌های Snap24 اصلاً بلوک استدلال نبودند

بلوک `.thinking` از دور اول درست کار می‌کرد (تست هم داشت). آنچه کارفرما در Snap24 دید
**کارت خروجی ابزار** (WebFetch) بود که کارفرما هم آن را «باکس استدلال» می‌شمارد. آن کارت
قاعدهٔ خودش را داشت: `max-height: 380px` و در حالت peek هم `132px` (~۸ خط). حالا:

- پنجرهٔ peek به `8.25em` (همان ۵ خط) رسید تا با بلوک استدلال یکی باشد؛
- تابع تازهٔ `settleTools()` با آمدن `text` بدنهٔ کارت‌ها را جمع می‌کند و فقط سطر عنوان
  می‌ماند (سابقه گم نشود)، مگر کاربر خودش بازش کرده باشد.

### ۱۶.۴ کارت سرویس، این بار واقعاً مثل Snap4

بازخورد صریح: «نه این دکمه‌های زمخت.» دو دکمهٔ پرِ هم‌وزن («باز کردن» + «تست») جای
پاورقی سبک مرجع را گرفته بودند. حالا:

| عنصر | مرجع Snap4 | حالا |
|---|---|---|
| کلیک اصلی | خود کارت | ✅ خود کارت |
| وضعیت | نقطهٔ رنگی گوشهٔ بالا | ✅ `.card-dot` |
| قابلیت | چیپ خاکستری `Chat` | ✅ `.cap-chip` |
| روشن/خاموش | سوییچ کوچک | ✅ `.btn.sw` |
| تست | «▶ Test» ریز | ✅ `.btn.icon-act` |

### ۱۶.۵ سه تستی که رفتار غلط را قفل کرده بودند

قاعدهٔ پروژه («هر دکمه کلاس `btn`») و دو تست ناوبری، کارت تازه را رد کردند. هر سه اصلاح
شدند — دو تای آخر حالا روی `.hub-card.linked` کلیک می‌کنند نه دکمهٔ حذف‌شده.

### ۱۶.۶ دو تست رگرسیون تازه

- **تماس واقعی از راه SOCKS**: یک SOCKS5 مینیمال بالا می‌آید و از راهش تماس زده می‌شود.
  با برگرداندن کد به `{ url }`، تست قرمز شد (جهش تأیید شد).
- **`syncProxyToHub` در بوت**.

**۳۷۷ تست موفق** (۲ تای تازه) + ۱ محیطی داکر.

### ۱۶.۷ درسی که باید ثبت شود

دور اول همه‌چیز را از روی **خواندن کد** تشخیص داد و تست‌ها را هم سبز کرد — ولی تست‌ها
مسیرهای شبکه‌ای را دابل می‌کردند، پس ناسازگاری کتابخانه‌ها هرگز اجرا نمی‌شد. **هر جا
یک وابستگی خارجی در مسیر است، حداقل یک تست باید واقعاً آن مسیر را اجرا کند** — حتی با
یک سرور محلی مینیمال. این همان چیزی است که این دور، دو باگ کشنده را در سی ثانیه لو داد.
